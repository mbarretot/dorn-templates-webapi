## Conventions

- **Use cases**: one folder per use case, `Application/<Feature>/<UseCase>/`, holding a request implementing `IRequest<T>`, a handler implementing `IRequestHandler<TRequest, TResponse>`, and an optional FluentValidation validator. Messaging comes from `Dorn.Messaging`. Handlers live only in the Application project.
- **Ports**: handlers depend on the repository ports in `Domain/Common/Interfaces`, never on ORM types.
- **Validation**: validators are found by assembly scan and run in `ValidationBehavior`; `ValidationExceptionHandler` turns failures into a `400` problem-details response.
- **Caching**: a query implementing `ICacheableQuery<T>` is cached in HybridCache; a command implementing `ICacheInvalidatingCommand` lists the keys it invalidates.
- **Endpoints**: a static class per feature in `WebApi/Endpoints` with a `Map<Feature>Endpoints` extension, called from `Program.cs`.
- **Cross-cutting**: a global rate limiter (`RateLimitingExtensions`), OpenTelemetry (`ObservabilityExtensions`), and `GET /health` are already wired.
- **Sample feature**: `Todos` is the reference implementation across every layer. Copy its shape for a new feature.

### Persistence

<!--#if (UseEfCore) -->
- The `DbContext` is `Infrastructure/Persistence/ApplicationDbContext.cs`; repositories are in `Infrastructure/Repositories/EfCore`.
- Change the schema with a migration: `dotnet ef migrations add <Name> --project src/CleanArchWebApi.Infrastructure --startup-project src/CleanArchWebApi.WebApi` (needs the `dotnet-ef` tool). Do not edit the migrations that shipped with the solution; they target the selected database only.
- `Program.cs` applies pending migrations at startup.
<!--#else -->
- Repositories are in `Infrastructure/Repositories/Dapper`; `DapperContext.CreateConnection()` is the only place a connection is opened.
- There is no migration tooling. `DapperContext.InitializeSchemaAsync` creates the schema at startup; extend it when you add a table.
- The expression-based `FindAsync`, `AnyAsync`, and `CountAsync` throw `NotSupportedException`. Add a dedicated repository method and hand-written SQL instead of relying on LINQ translation.
<!--#endif -->
<!--#if (UseSqlite) -->
- The connection string is `ConnectionStrings:Default` in `src/CleanArchWebApi.WebApi/appsettings.json`. It is file based and needs no external service.
<!--#elseif (UseSqlServer) -->
- The connection string is `ConnectionStrings:CleanArchWebApi`, a SQL Server connection.
<!--#else -->
- The connection string is `ConnectionStrings:CleanArchWebApi`, a PostgreSQL connection.
<!--#endif -->
<!--#if (!UseSqlite && UseAspire) -->
- Aspire provisions the database and injects that connection string into the API, so it overrides `appsettings.json` when you run the `AppHost`.
<!--#elseif (!UseSqlite && UseCompose) -->
- `docker-compose.yml` starts the database and sets that connection string for the API service, so it overrides `appsettings.json` under Compose.
<!--#elseif (!UseSqlite) -->
- Nothing provisions the database here: point `ConnectionStrings__CleanArchWebApi` at a running server before `dotnet run`.
<!--#endif -->
<!--#if (HasConnectionString) -->
- A connection string was supplied at generation time and is stored in clear text in the generated configuration.
<!--#endif -->
- Never put secrets in `appsettings.json`; use `dotnet user-secrets` or environment variables for credentials.

### Authentication and authorization

<!--#if (UseCustomAuth) -->
- Tokens are self-issued: `Jwt:Issuer`, `Jwt:Audience`, and `Jwt:SigningKey` live in the `Jwt` section. Set the signing key with `dotnet user-secrets` or `Jwt__SigningKey`; outside Development, startup throws while it is a placeholder.
- `POST /auth/login` returns an access token and a refresh token; `POST /auth/refresh` rotates the pair. Only a SHA-256 hash of the refresh token is stored, and replaying a rotated token revokes the user's whole chain.
- `Program.cs` seeds a demo user from `AuthSeed:DemoEmail` and logs its generated password in Development. Replace this seeding before deploying.
- Custom authentication needs EF Core: `AppUser` and its migrations do not exist under Dapper.
<!--#endif -->
<!--#if (UseAzureAdAuth) -->
- Tokens are validated only, with `Microsoft.Identity.Web` and the `AzureAd` section. Replace the `REPLACE_ME_*` tenant and client ids. There is no login endpoint and no user store.
<!--#endif -->
- Endpoints require permission policies. The permission strings are constants in `Application/Common/Security/Permissions.cs`; `PermissionAuthorizationHandler` checks a `permission` claim. To protect a new endpoint, add a constant to `Permissions.All` and call `RequireAuthorization(Permissions.<Name>)`.
<!--#if (UseAzureAdAuth) -->
- Entra ID must be configured (App Roles or a claims-mapping policy) to emit a `permission` claim with those exact values.
<!--#endif -->
- `GET /api/me` echoes the caller's claims and is useful for debugging tokens.
<!--#else -->
Authentication is not generated. Do not assume a caller identity exists, and do not add `[Authorize]`-style checks without also adding authentication.
<!--#endif -->

## Commands

Run everything from the solution root.

| Task | Command |
| --- | --- |
| Restore the local tools | `dotnet tool restore` |
| Build | `dotnet build` |
<!--#if (UseAspire) -->
| Run | `dotnet dorn run`, or `dotnet run --project src/CleanArchWebApi.AppHost` |
<!--#elseif (UseCompose) -->
| Run | `dotnet dorn run`, or `docker compose up --build` |
<!--#else -->
| Run | `dotnet run --project src/CleanArchWebApi.WebApi` |
<!--#endif -->
<!--#if (IncludeTests) -->
| Test everything | `dotnet test` or `dotnet dorn test` |
| Test one tier | `dotnet dorn test --tier <name>` or `dotnet test tests/CleanArchWebApi.<Tier>.Tests` |
| Coverage gate | `dotnet dorn coverage` |
<!--#endif -->
| Format | `dotnet format` |
| Check formatting | `dotnet format --verify-no-changes` |

Formatting follows `.editorconfig` and is enforced by `dotnet format`. Format before you finish, and never reformat files you did not change.

## Test tiers

| Tier | Project | Verifies | Needs |
| --- | --- | --- | --- |
| Application | `tests/CleanArchWebApi.Application.Tests` | Handlers, validators, and behaviors, with NSubstitute doubles | Nothing |
<!--#if (UseSqlite) -->
| Integration | `tests/CleanArchWebApi.Integration.Tests` | Persistence against the real database | Nothing |
<!--#else -->
| Integration | `tests/CleanArchWebApi.Integration.Tests` | Persistence against the real database | A container runtime; Testcontainers starts the database |
<!--#endif -->
| Architecture | `tests/CleanArchWebApi.Architecture.Tests` | The layering rules above, with ArchUnitNET | Nothing |
<!--#if (UseDapper && !UseSqlite) -->
| Functional | `tests/CleanArchWebApi.Functional.Tests` | The HTTP pipeline through `WebApplicationFactory<Program>` | A container runtime; Testcontainers starts the database |
<!--#else -->
| Functional | `tests/CleanArchWebApi.Functional.Tests` | The HTTP pipeline through `WebApplicationFactory<Program>`, on its own throwaway database | Nothing |
<!--#endif -->

- Tests use xUnit with plain `Assert.*`; there is no assertion library or mocking framework beyond NSubstitute in the Application tier.
- Put a new test in the tier that owns the behavior: a handler in Application, a route in Functional, a persistence query in Integration.
- The test tiers bring their own database. They never read the connection string from `appsettings.json`.
<!--#if (UseAuth) -->
- Functional tests replace the real authentication scheme with one that always succeeds and grants every permission, except where authorization itself is under test.
<!--#endif -->

## Never

- Reference `Application`, `Infrastructure`, `WebApi`, or an ORM from `Domain`, or `Infrastructure` and `WebApi` from `Application`.
- Put business rules in endpoints or in `Infrastructure`.
- Register OpenTelemetry a second time: it is wired once already.
- Commit secrets.
